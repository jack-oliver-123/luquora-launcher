# Luquora Launcher v0.1 设计

日期：2026-11-13

状态：用户已于 2026-11-13 确认；尚未开始产品代码实现。

## 1. 已确认的决定

- 产品名称为 **Luquora Launcher**，缩写 **LQL**。
- 首先支持 Windows 上的 Minecraft Java 版。
- 采用三阶段方向：可靠安装与启动 → 模组和整合包 → 选择差异化功能。
- 本次实现聚焦第一阶段。
- 技术路线为 **Electron + Vue 3 + TypeScript**。

用户尚未逐项确认的细节，以下标为设计提案或实现者决定，不视为既有用户要求。

## 2. 目的与成功标准

让玩家在 Windows 上完成账号添加、游戏安装、Java 配置和游戏启动，并在失败时获得明确、可导出的排错信息。

基础成功路径：

1. 在没有预装 Java 的受支持 Windows 环境中打开 LQL。
2. 添加拥有 Java 版游戏使用权限的微软账号。
3. 创建一个实例并选择受支持的原版正式版。
4. 下载游戏及其依赖，自动提供兼容的 Java。
5. 进入游戏主菜单，正常退出，LQL 显示退出状态并保留日志。
6. 创建第二个实例，证明两个实例的存档和配置互不干扰。

不能把“窗口能显示”“构建成功”“使用模拟登录/启动事件”视为完成上述目标。真实认证和真实游戏启动必须单独验收。

## 3. 首版范围提案

### 3.1 平台与版本

- 正式支持 Windows 10/11、x64。Windows 7/8、32 位、ARM64 和其他桌面系统不列入 v0.1 验收。
- 首版仅提供原版正式版安装，不提供快照、预发布版、远古版本入口。
- 安装列表按服务端元数据提供正式版，明确不承诺全部历史版本均已验证。
- 首轮兼容性验收固定为 **1.16.5、1.20.1、26.3**。26.3 是本次实时读取 Mojang manifest 得到的最新正式版；后续发布的新版本不自动扩大首版验收范围。
- 上述平台、版本范围是为了使验收可执行而提出的默认值，可在用户确认设计时调整。

### 3.2 功能

| 模块 | v0.1 包含 | 本阶段不包含 |
| --- | --- | --- |
| 微软账号 | 浏览器授权；多个账号保存与切换；会话刷新；重新授权；移除本地账号；权限/角色检查 | 用户名密码表单、第三方认证服务器、离线自定义身份 |
| 游戏版本 | 获取正式版列表；创建原版实例；安装游戏、依赖库、资源和 natives；必要文件校验与补全 | Forge、NeoForge、Fabric、Quilt、OptiFine |
| 实例 | 创建、选择、重命名、查看目录、删除；独立存档和配置；每实例设置 | 并行启动多个游戏、实例导入导出、复制、整合包 |
| Java | 检测本地 Java；读取版本与架构；按游戏要求选择；缺失时下载；允许显式选择路径 | 修改系统 PATH/JAVA_HOME、要求用户手工配置全局 Java |
| 下载 | 阶段和字节进度；有限并发；取消；失败重试；完整性校验；重启后复用已校验文件 | 运行中暂停/继续、持久化任务队列、镜像自动测速、独立代理配置 |
| 启动设置 | 最大内存、窗口宽高、窗口/全屏、Java 路径；全局默认与实例覆盖 | JVM 参数编辑器、启动脚本和前后置命令 |
| 日志 | 下载/启动阶段错误；游戏 stdout/stderr；退出状态；日志查看和导出 | 自动修复所有问题、模组冲突分析、自动上传日志 |
| 分发 | Windows x64、当前用户安装包；第三方许可清单 | 自动更新服务、强制管理员安装、代码签名承诺 |

微软服务不接受某账号、账号缺少相应权限或游戏角色时，应显示具体类别的错误，不能把认证降级为离线账号后继续启动。

### 3.3 完成顺序

实现从风险较高的依赖兼容性、认证可行性和真实安装/启动开始，再补全产品交互与分发。不得先把全部界面完成，最后才验证核心库能否在打包后的 Electron 中工作。

## 4. 已比较的技术路线

| 方案 | 优点 | 取舍 | 决定 |
| --- | --- | --- | --- |
| Electron + Vue 3 + TypeScript | Vue 界面开发；Node 原生处理文件和进程；可评估 TypeScript 启动器核心库 | 桌面运行环境和安装包开销较高 | 用户已选择 |
| Tauri + Vue + Rust | Web 界面配合较轻的桌面壳 | 同时维护 Rust/前端；本次所评估 Node 核心库不能直接作为原生核心使用 | 本次不采用 |
| C# + WPF | Windows 进程和系统集成直接 | 不使用 Vue 界面栈；未来跨平台需要重新评估 | 本次不采用 |

选定 Electron 后，优先使用小而明确的核心库接口处理 Minecraft 格式和安装细节，LQL 自己负责用户流程、状态、持久化和错误处理。没有必要复制完整 XMCL 应用或引入其联机、资源池等整套架构。

## 5. 技术与依赖边界

### 5.1 基础工具

- Electron、Vue 3、TypeScript、Vite。
- 包管理器默认采用 npm，提交锁文件。工具版本在实施计划的依赖验证步骤中确定，避免把 GitHub 默认分支的开发版本直接当作可安装的 npm 版本。
- 使用一个应用工程；不引入 monorepo、多进程业务微服务或独立后端。
- 具体打包工具由实现者选择，以能产生可运行的 Windows x64 当前用户安装包为准。

### 5.2 启动器核心

优先验证以下候选库：

- `@xmcl/core`：游戏版本描述解析、启动参数及进程启动能力。
- `@xmcl/installer`：原版文件、依赖及相关运行时安装能力。
- `@xmcl/user`：微软身份令牌之后的 Xbox/Minecraft 认证相关能力。
- `@azure/msal-node`：微软 OAuth 交互和令牌缓存。

本次读取的 XMCL 源码中，三个包的 `package.json` 均声明 MIT。`@xmcl/user` README 明确说它不覆盖微软 OAuth 首步，不能把它当作完整登录方案。相关包当前源码声明的 Node 要求及传递依赖，也必须与最终 Electron 的内嵌 Node 版本一起核对。[S1]—[S5]

安装依赖前验证 npm 实际发布内容、许可和跨包兼容性；锁定可用组合。若这些核心库无法支持目标游戏版本、认证或打包环境，应停止对应实现并报告差异，更新方案后再继续，不能隐瞒为“后续再补”的占位实现。

### 5.3 独立身份

- 使用 LQL 自己的微软应用标识。不得使用示例中、XMCL、Prism 或其他启动器的应用标识和 API 密钥。
- 公共桌面客户端不保存应用 client secret。
- 首版无 CurseForge 集成，因此不申请或配置其 API 密钥。
- 不复制其他启动器的品牌资源。LQL 自身的项目许可证尚未由用户选择；本设计不替用户决定开源或闭源。

## 6. 应用边界

### Electron 主进程

- 管理账号会话、元数据请求、文件、Java 检测、安装任务、游戏进程与日志。
- 校验所有 renderer 输入，执行实际操作。
- 不在 renderer 内持有刷新令牌或完整认证缓存。

### Preload

- 通过 `contextBridge` 暴露有限且有类型的业务方法。
- 不暴露任意文件读写、任意命令执行或原始 `ipcRenderer`。
- 对事件订阅提供取消订阅能力，避免页面切换后重复接收进度。

### Vue renderer

- 呈现账号、实例、安装进度、启动状态、设置与日志。
- 发送业务请求，展示经过脱敏的结果。
- 开启上下文隔离和 renderer sandbox，关闭 renderer 的 Node 集成。
- 微软授权与外部帮助通过受控的系统浏览器入口打开，不加载任意远程页面进入有权限的应用窗口。

具体目录结构与 IPC 命名由实现者决定。文件系统/进程边界必须明确，但不为只有一种实现的模块建立可插拔框架。

## 7. 认证设计

1. 用户发起“添加微软账号”。
2. 主进程通过 MSAL Node 公共客户端发起设备代码授权，界面显示验证码和授权地址，可由用户打开系统浏览器完成登录。一次只允许一个交互式授权任务。
3. 主进程用微软令牌获取 Xbox/XSTS 及 Minecraft 访问令牌，随后读取账号的游戏权限和 Minecraft profile；只有获取到可用身份才写入账号列表。
4. renderer 只接收账号标识、显示名、UUID 和登录状态，不接收访问/刷新令牌。
5. 游戏启动前检查会话；优先尝试静默刷新。失效、被撤销或需要交互时，要求重新登录。
6. 移除账号会删除其本地令牌缓存及关联账号记录；不修改微软账户本身。

缓存使用 Electron `safeStorage` 加密后写入磁盘，解密只在主进程进行。加密不可用时不写入明文缓存，当前进程的会话可以继续使用，并提示下次需重新登录。

`safeStorage` 在 Windows 上提供与系统登录用户相关的保护，并不能阻止同一用户上下文中的其他应用读取秘密；产品说明不能承诺超出这一边界的安全性。[S6][S7]

设备代码授权必须有取消、超时和过期处理，轮询按服务端规定间隔执行。代码、完整授权地址和认证响应不写入日志。

微软应用注册、服务访问要求及真实账号是否可用，是首个外部依赖检查项。具体注册权限和接入资格必须按实际服务反馈核实，不能承诺仅有 client ID 就一定能完成 Minecraft 认证。需要用户控制的账号/云端设置时，整理准确步骤和当前结果后交给用户处理；其他本地工作可继续，真实认证验收保持未完成。

## 8. 数据与实例隔离

### 8.1 本地存储

- 默认用户数据根目录：`%APPDATA%\LuquoraLauncher`。
- 普通设置和实例元数据采用 JSON，写入使用同目录临时文件加原子替换，不引入数据库。
- 设置含 `schemaVersion`；首版仅校验当前格式，不建立通用迁移框架。
- 令牌缓存独立加密保存；日志、普通设置、实例元数据不包含令牌。
- 默认游戏数据根目录：用户数据根目录下的 `game-data`。允许在创建第一个实例前选择其他目录；存在实例后 v0.1 不支持自动迁移整个根目录。

### 8.2 游戏目录

- `game-data/instances/<instance-id>/game`：该实例的存档、配置、截图、模组等可变文件。
- `game-data/shared`：可校验且可重新下载的 assets、libraries 和版本描述等共享依赖。
- `game-data/runtimes`：按运行时标识保存的启动器管理 Java。
- `game-data/logs`：按启动会话归档的脱敏日志。
- 实例 ID 由启动器生成，不以实例显示名作为目录名；重命名不移动目录。

实例元数据至少包含 ID、显示名、Minecraft 版本、创建时间、安装状态和实例设置覆盖。共享依赖路径与游戏工作目录分别传入启动核心，不能把共享目录作为所有实例的 `gameDir`。

配置损坏时保留原文件并提示恢复，不静默覆盖导致实例“消失”。不因某个配置项不合法而删除整个用户数据根目录。

### 8.3 删除

- 删除实例前显示实例名和实际目录，并要求确认。
- 运行中或有安装任务的实例不能直接删除。
- 首版将实例专属目录移入 Windows 回收站，成功后再删除元数据；回收站操作失败就保留实例并报告，不自动改成永久删除。
- 删除不清理共享依赖或其他实例；共享缓存垃圾回收留到后续。
- 主进程必须验证目标是数据根目录内对应实例的受管子目录。不能只依赖字符串前缀判断，必须处理路径规范化和重解析点边界。

## 9. 版本安装与 Java

### 9.1 元数据

- 从 Mojang 官方版本 manifest 获取版本列表和版本描述，不在应用中固定最新版本号。
- 使用元数据提供的文件地址、尺寸和摘要验证依赖；下载完成但未通过校验的文件不标为可用。
- 官方源是 v0.1 的下载来源。镜像和独立代理选项留待后续，网络失败必须可理解且可重试。
- 对版本描述、运行时清单与解压目标进行格式和路径校验，不允许文件逃逸出相应安装目录。

### 9.2 安装任务

- 首版同一时间只执行一个安装任务，避免多任务共享依赖竞争；账号授权和设置浏览不因此被阻塞。
- 阶段为元数据、Java、游戏文件、依赖/资源、校验、完成。
- 保留旧的可用文件，下载使用临时文件；校验完成后再替换。
- 网络中断提供有限自动重试，达到上限后由用户重试。重试重新检查文件，只下载缺失或损坏内容。
- 取消后实例标记为未完成，已校验文件保留。重启后也可重新发起安装；这不等同于持久化暂停/恢复任务。
- 安装中关闭 LQL 时，确认取消安装并退出，或取消关闭；取消安装后等待任务停止写入再退出。同一实例安装中不能启动，运行中不能重新安装。
- 进度不提供虚假的总体百分比：总量未确定时显示阶段；确定后显示阶段字节或文件进度。

### 9.3 Java 选择

- 优先读取游戏元数据中的 `javaVersion`、平台架构和运行时组件标识，不能把所有新版本映射为 Java 21。
- 候选为用户显式选择的 Java、LQL 管理运行时，以及系统已安装的兼容 Java。显式选择不兼容时说明原因，不静默改成另一路径启动。
- 自动选择优先使用满足要求的已管理/已检测运行时；缺失时获取对应的 Mojang 运行时清单并校验安装。
- 已安装 Java 的检测范围包括 LQL 运行时目录、显式路径、常见注册表/安装位置、环境中的候选路径。不能对所有磁盘做无边界递归扫描。
- 执行 Java 版本探测时设超时，检查架构和执行结果，不仅判断文件是否存在。
- 第一轮已核实的基线为：1.16.5 → Java 8 / `jre-legacy`；1.20.1 → Java 17 / `java-runtime-gamma`；26.3 → Java 25 / `java-runtime-epsilon`。[S8]—[S11]
- 缺少 Java 元数据的历史版本暂不进入首版验收；后续如要支持，再加入有证据的兼容规则。

## 10. 游戏进程与状态

- 首版同一时间只允许一个游戏进程；多实例表示管理多个独立环境，不表示并发运行。
- Electron 应用使用单实例锁，避免两个 LQL 进程同时修改相同状态。
- 启动前完成账号、文件、Java 和设置校验；按钮操作防重复。
- 使用参数数组创建进程，不经过命令行 shell；在 Windows 下不额外弹出终端窗口。
- 版本安装状态与游戏运行状态分开记录。安装状态至少有未完成、可启动；进程状态至少有空闲、检查中、启动中、运行中、已退出、失败。
- 进程已创建不等于成功进入游戏。产品显示启动进度和进程状态，进入主菜单作为人工验收项。
- 捕获 stdout/stderr、进程启动错误、退出码和用户停止操作。用户主动停止与异常崩溃分别展示。
- 用户停止游戏时先确认，再尽量正常终止并等待退出；超时后提供强制结束选择。不把单次 `kill` 调用视为已确认退出。
- 游戏运行时关闭 LQL：确认“结束游戏并退出”或取消关闭；首版不提供托盘或与启动器脱离的后台运行模式。
- 安装任务和进程的活动状态只在当前应用会话中成立，重启时不能直接恢复为“下载中”或“运行中”。应用异常退出后若游戏仍存活，检测到与受管实例关联的残留进程时阻止该实例的启动、重装和删除，并提示用户结束游戏；不得仅凭旧 PID 结束可能已被复用的其他进程。

## 11. 设置、日志与错误

### 11.1 设置

- 全局默认值应用于没有覆盖值的实例，实例仅保存显式覆盖。
- 内存必须为正整数，并在应用可用内存和运行时限制内校验；默认值按设备内存给出保守建议，实现者决定具体公式并测试边界。
- 分辨率为正整数并设合理上下限；路径必须可访问，Java 可执行文件必须通过探测。
- 选中账号和实例持久化；删除当前项后选择其他可用项，否则呈现空状态。

### 11.2 日志

- 写入安装/启动阶段、错误类别、必要的路径和版本信息，不记录完整含令牌的启动命令。
- 游戏原始输出也经过令牌脱敏再展示或落盘；错误对象和 HTTP 失败体不能绕过脱敏。
- 日志显示区域限制缓冲行数；磁盘日志按大小和会话数量设保留上限，实现者选择具体默认值。
- 导出为本地日志文件，附游戏版本、Java 版本、LQL 版本和退出状态。告知用户文件可能包含本地路径及游戏中的内容，由用户自行决定分享。
- 首版不上传日志，不收集遥测，不添加广告或远程脚本。

### 11.3 错误分类

至少区分网络超时/服务失败、授权取消/过期、缺少游戏权限或角色、磁盘不足/目录不可写、文件校验失败、Java 缺失/不兼容、进程创建失败、游戏异常退出。

每类提供发生阶段、可执行的下一步和查看日志入口。不得把所有错误转换为“启动失败，请重试”。

| 自动化逻辑测试 | 元数据解析；Java 要求/选择；设置覆盖；下载取消和坏文件重试；路径边界；令牌脱敏 | 针对异常输入和真实边界的通过用例，避免只镜像实现的测试 |
| 集成测试 | 临时目录内安装/校验流程；IPC 输入拒绝；进程错误与退出状态；加密缓存不可用处理 | 可重复测试结果，模拟网络和进程需明确标识 |
| 界面验证 | 空账号/空实例；下载中/取消/失败重试；账号失效；游戏运行时操作限制；窗口关闭确认 | 实际 Electron 应用操作记录；不只浏览器中模拟 preload |
| 真实认证 | 用 LQL 自有配置完成微软 → Xbox → Minecraft，并在应用重启后刷新会话 | 用户授权的真实测试结果；没有凭据时明确未验收 |
| 真实游戏 | 三个基线版本进入主菜单并退出；无预装 Java 时自动处理；两个实例不混用数据 | Windows 实机结果和对应日志；无显示环境不宣称已验证主菜单 |
| Windows 边界 | 中文/空格路径、目录不可写、网络中断、取消任务、Java 不兼容、磁盘不足等 | 实机验证或受控可重复测试，注明类型 |
| 打包产物 | 安装后读取本地资源、IPC、核心库和 Java 进程均可用 | 安装包生成及安装后实际运行结果 |

新增工程可从开始建立必要测试。修复已发现的问题时先复现，再验证修复；仅文案/样式等低影响改动不额外建立低价值测试。

交付包括源码、可运行的开发命令、Windows 打包方式、第三方许可清单、首版使用说明、已通过/未通过/因外部条件未验收的清单。不自动提交、推送、创建分支或发布安装包到外部平台。

## 13. 留给实现者的决定

- 源码目录、内部函数/IPC 命名、构建与测试工具的具体版本。
- npm 上实际可安装且彼此兼容的依赖组合，按验证结果锁定。
- 有限下载并发数、重试次数、日志上限和内存推荐公式。
- 不改变功能范围的界面布局、视觉风格和组件细节；需要用可查看的设计或运行结果验证，不将品牌图标等第三方素材直接带入 LQL。
- 首版所需的最小模块拆分，不建设插件系统或通用任务调度框架。

若发现用户目标与依赖限制矛盾、需加入服务端、必须更换技术栈或无法完成真实认证，应说明证据并调整设计，而非默默扩大范围或降低验收标准。
